## 1. 소개

지금 여행자는 온보딩 마지막 단계에서 "반나절(4시간)" 또는 "종일(8시간)"만 고를 수 있고, 코스는 항상 10:00에 시작한다. 오후 2시에 앱을 연 여행자도 10:00부터 시작하는 코스를 받는다.

이 기능은 여행자가 **시작 시각**과 **끝나는 시각**을 직접 고르게 한다. 코스는 그 시간 안에 들어가도록 짜이고, 도착했을 때 문을 연 장소만 들어간다.

현재 코드 상태:

- 백엔드 `POST /courses`는 이미 `start_time`을 받는다 (`backend/app/schemas.py`의 `CreateCourseRequest`). 프론트가 보내지 않아서 항상 기본값 10:00이 쓰인다.
- 코스 길이는 `user_profile.duration` (`half_day` | `full_day`)로만 정해진다 (`backend/app/planner.py`의 `new_course`, `replan`).
- 장소의 `opening_hours`는 사람이 읽는 문장이다 (예: `"09:00-18:00 (last entry 17:30)"`). 코드가 비교할 수 없어서 지금은 휴무 요일(`closed_days`)만 거른다.

## 2. 목표

- 여행자가 시작 시각과 끝나는 시각을 30분 단위로 고를 수 있다.
- 코스의 모든 정류장이 고른 시간 안에 시작하고 끝난다.
- 코스의 모든 정류장이 그 장소의 영업시간 안에 시작하고 끝난다.
- 재계획(비, 휴무, 배고픔, 피곤함) 뒤에도 위 두 조건이 유지된다.
- 이미 저장된 코스(`duration`만 가진 옛 코스)가 계속 열리고 재계획된다.

## 3. 사용자 스토리

### US-T01: 장소에 여는 시각과 닫는 시각 필드 추가
**설명:** 개발자로서, 코드가 영업시간을 비교할 수 있도록 장소마다 여는 시각과 닫는 시각을 정해진 형식으로 저장하고 싶다.

**완료 조건:**
- [ ] `places`에 `open_time`, `close_time` 필드를 추가한다. 형식은 `"HH:MM"` 문자열이고 둘 다 `null`일 수 있다
- [ ] `null`은 "항상 열려 있음"을 뜻한다 (예: 용두암). 둘 중 하나만 `null`인 장소는 없다
- [ ] 자정 이후까지 여는 장소는 `close_time`을 `"24:00"`으로 적는다
- [ ] 계절이나 요일에 따라 시간이 다르면 가장 짧은 기본 시간을 적는다 (예: 제주목관아는 야간 개장을 빼고 `09:00`~`18:00`). 입장 마감이 따로 있으면 `close_time`은 입장 마감이 아니라 문 닫는 시각을 적는다
- [ ] 현재 19곳 모두 값을 채운다. 기존 `opening_hours` 문장은 화면 표시용으로 그대로 둔다
- [ ] `backend/sql/schema.sql`, `backend/app/data/places.json`, `data/seed`의 원본 파일, `backend/scripts/build_places.py`, `backend/scripts/seed_supabase.py`가 새 필드를 다룬다
- [ ] `build_places.py`는 형식이 틀린 값(`"9:00"`, `open_time` ≥ `close_time`)을 만나면 오류로 멈춘다
- [ ] 백엔드 테스트(`pytest`)가 통과한다

### US-T02: 코스 요청이 시작 시각과 끝나는 시각을 받는다
**설명:** 개발자로서, API가 `duration` 대신 시작 시각과 끝나는 시각을 받게 해서 코스 길이를 자유롭게 정하고 싶다.

**완료 조건:**
- [ ] `CreateCourseRequest`는 `start_time`과 `end_time`을 둘 다 필수로 받는다 (`"HH:MM"`)
- [ ] `UserProfileIn`에서 `duration`을 뺀다. `duration`을 보내면 422가 난다 (`extra="forbid"` 유지)
- [ ] 아래 조건을 하나라도 어기면 422와 코드 `INVALID_TIME_WINDOW`를 돌려준다
  - `start_time`은 `08:00` 이상 `16:00` 이하
  - 두 값 모두 분이 `00` 또는 `30`
  - `end_time` − `start_time`은 120분 이상 600분 이하
  - `end_time`은 `22:00` 이하
- [ ] 서버는 저장하는 `user_profile`에 `start_time`과 `end_time`을 넣는다 (`conditions`처럼 서버가 채우는 값)
- [ ] 정류장 수의 최소·최대는 FR-6의 식으로 정한다. 240분이면 3~4곳, 480분이면 5~7곳으로 지금과 같다
- [ ] 위 검증 조건마다 테스트가 하나씩 있고 `pytest`가 통과한다

### US-T03: 영업시간 안에만 정류장을 넣는다
**설명:** 여행자로서, 도착했을 때 문이 닫혀 있지 않도록 내가 머무는 동안 열려 있는 장소만 코스에 들어가기를 원한다.

**완료 조건:**
- [ ] 후보 필터에 규칙을 추가한다: 장소의 영업시간과 여행 시간이 겹치는 길이가 `avg_stay_min`보다 짧으면 후보에서 뺀다
- [ ] 규칙 플래너(`rule_plan`)는 도착 시각이 `open_time`보다 이르거나, 도착 시각 + 체류 시간이 `close_time`보다 늦는 장소를 고르지 않는다
- [ ] LLM 입력의 후보마다 `open_time`, `close_time`을 넣고, 프롬프트(`backend/app/llm.py`)에 "머무는 시간이 영업시간 안에 있어야 한다"는 규칙을 한 줄 추가한다
- [ ] 시각 계산(`schedule`) 뒤에 영업시간을 어기는 정류장은 코스에서 빼고, 남은 정류장의 시각을 다시 계산한다. 어기는 정류장이 없을 때까지 반복한다
- [ ] 다 빼고 나서 정류장이 하나도 없으면 409 `NO_CANDIDATES`를 돌려준다
- [ ] `open_time`이 `null`인 장소는 이 규칙을 항상 통과한다
- [ ] 테스트: 16:00~18:00 여행에 `close_time`이 `17:00`이고 체류가 90분인 장소가 들어가지 않는다
- [ ] `pytest`가 통과한다

### US-T04: 재계획이 저장된 끝나는 시각을 쓴다
**설명:** 여행자로서, 여행 중에 코스를 다시 짜도 처음 고른 끝나는 시각을 넘지 않기를 원한다.

**완료 조건:**
- [ ] `replan`은 끝나는 시각을 `user_profile.end_time`에서 읽는다
- [ ] `user_profile`에 `end_time`이 없고 `duration`만 있는 옛 코스는 지금 방식(첫 정류장 시작 시각 + 240분 또는 480분)으로 계산한다
- [ ] 재계획으로 새로 들어온 정류장에도 US-T03의 영업시간 규칙이 적용된다
- [ ] `backend/scripts/reset_emma.py`와 `data/demo`의 데모 코스가 새 형식(`start_time`, `end_time`)으로 동작한다
- [ ] 테스트: 옛 형식 코스와 새 형식 코스를 각각 재계획하는 테스트가 통과한다

### US-T05: 온보딩에서 시작 시각과 끝나는 시각 고르기
**설명:** 여행자로서, 내가 실제로 놀 수 있는 시간에 맞는 코스를 받도록 시작 시각과 끝나는 시각을 고르고 싶다.

**완료 조건:**
- [ ] 온보딩 5단계의 제목을 `"When is your day?"`로 바꾸고, 반나절/종일 버튼을 없앤다
- [ ] "Start" 선택 상자: `08:00`부터 `16:00`까지 30분 단위. `16:00`보다 늦은 시각은 목록에 없다
- [ ] "End" 선택 상자: 시작 시각 + 2시간부터, 시작 시각 + 10시간과 `22:00` 중 이른 시각까지 30분 단위
- [ ] 시작 시각의 처음 값은 기기의 현재 시각을 30분 단위로 올린 값이다 (14:10 → 14:30). 현재 시각이 08:00 전이면 `08:00`, 16:00 뒤면 `10:00`이다
- [ ] 끝나는 시각의 처음 값은 시작 시각 + 4시간이다 (위 상한을 넘으면 상한)
- [ ] 시작 시각을 바꿔서 끝나는 시각이 허용 범위를 벗어나면, 끝나는 시각을 시작 시각 + 4시간(상한 적용)으로 다시 맞춘다
- [ ] 두 선택 상자 아래에 길이를 글로 보여준다 (예: `"4 h 30 min"`)
- [ ] "Create my day"를 누르면 `start_time`과 `end_time`이 요청에 들어가고 `duration`은 들어가지 않는다
- [ ] `frontend/lib/types.ts`의 `UserProfileInput`에서 `duration`을 빼고, `api.createCourse`가 두 시각을 필수 인자로 받는다
- [ ] 서버가 `INVALID_TIME_WINDOW`를 돌려주면 5단계에 머물며 `"Please check your start and end time."`를 보여준다
- [ ] 타입 검사와 린트가 통과한다
- [ ] dev-browser 스킬로 브라우저에서 확인한다: 14:00~17:00으로 코스를 만들면 첫 정류장이 14:00에 시작하고 마지막 정류장이 17:00 전에 끝난다

## 4. 기능 요구사항

- FR-1: 시스템은 장소마다 `open_time`과 `close_time`(`"HH:MM"` 또는 둘 다 `null`)을 저장해야 한다.
- FR-2: `POST /courses`는 `start_time`과 `end_time`을 필수로 받아야 한다.
- FR-3: 시스템은 `start_time`이 `08:00`~`16:00`이고, 두 시각이 30분 단위이며, 길이가 120~600분이고, `end_time`이 `22:00` 이하인 요청만 받아야 한다. 아니면 422 `INVALID_TIME_WINDOW`를 돌려준다.
- FR-4: `user_profile`은 `duration`을 더 이상 받지 않는다.
- FR-5: 시스템은 저장하는 `user_profile`에 `start_time`과 `end_time`을 기록해야 한다.
- FR-6: 정류장 수는 여행 길이 `h`(시간, 예: 4.5)로 정한다. `반올림(x) = floor(x + 0.5)`일 때
  - 최소 = `max(2, 반올림(h × 0.65))`
  - 최대 = `max(최소, 반올림(h × 0.9))`
  - 예: 2시간 → 2~2곳, 4시간 → 3~4곳, 8시간 → 5~7곳, 10시간 → 7~9곳
- FR-7: 코스의 모든 정류장은 `start_time` 이후에 시작하고 `end_time` 이전에 끝나야 한다 (지금의 규칙 유지).
- FR-8: 코스의 모든 정류장은 `open_time` 이후에 시작하고 `close_time` 이전에 끝나야 한다. `null`인 장소는 항상 통과한다.
- FR-9: FR-8은 새 코스와 재계획 모두에, 그리고 LLM 경로와 규칙 경로 모두에 적용된다.
- FR-10: 점심 규칙은 바꾸지 않는다. 여행 시간이 점심 시간대를 포함할 때만 식당 1곳을 넣는다 (`window_has_lunch`).
- FR-11: 재계획은 `user_profile.end_time`을 끝나는 시각으로 쓴다. 이 값이 없는 옛 코스는 `duration`으로 계산한다.
- FR-12: 온보딩 5단계는 시작 시각과 끝나는 시각 선택 상자 두 개와 길이 표시로 이루어진다.
- FR-13: 시작 시각의 처음 값은 현재 시각을 30분 단위로 올린 값이며, 허용 범위 밖이면 US-T05의 규칙을 따른다.

## 5. 다루지 않는 것

- 저녁 식사 정류장. 점심 시간대가 지난 코스에는 식당이 들어가지 않는다 (카페는 들어갈 수 있다).
- 08:00 이전이나 16:00 이후에 시작하는 코스, 22:00 이후에 끝나는 코스, 야간 코스.
- 날짜 고르기. 코스는 항상 오늘(한국 시간) 기준이며 휴무 요일도 오늘로 본다.
- 이틀 이상의 일정.
- 계절별·요일별 영업시간, 브레이크 타임, 입장 마감 시각.
- 코스를 만든 뒤에 시간을 바꾸는 기능. 바꾸려면 온보딩을 다시 한다.
- 출발 지역 고르기 (`tasks/prd-start-area.md`에서 다룬다).

## 6. 디자인 고려사항

- 화면 문구는 지금처럼 영어다.
- 선택 상자는 기본 `<select>`를 쓴다. 휴대폰에서 기본 휠 선택기가 뜨므로 따로 만들 필요가 없다.
- 테두리, 둥근 모서리, 글자 크기는 온보딩의 `Choice` 버튼과 맞춘다 (`frontend/app/onboarding/page.tsx`).
- 시각은 24시간 형식(`14:30`)으로 보여준다. 코스 화면이 이미 이 형식이다.

## 7. 기술 고려사항

- 바꿀 파일: `backend/app/schemas.py`, `planner.py`, `llm.py`, `main.py`, `config.py`, `backend/sql/schema.sql`, `backend/scripts/*`, `backend/tests/*`, `frontend/app/onboarding/page.tsx`, `frontend/lib/types.ts`, `frontend/lib/api.ts`.
- 허용 범위 값(`08:00`, `16:00`, `22:00`, 120, 600)은 `backend/app/config.py`에 둔다. 지금의 `HALF_DAY_MIN`, `FULL_DAY_MIN`은 옛 코스 재계획에만 쓰이므로 남긴다.
- Supabase의 `places` 테이블에 열을 추가해야 한다. 열 추가 SQL과 재시드 순서를 README에 적는다.
- 프론트와 백엔드를 따로 배포하면 그 사이에 옛 프론트가 `duration`을 보내 422가 난다. 백엔드와 프론트를 같이 배포한다.
- 시작 시각의 처음 값은 기기 시각으로 계산한다. 여행자가 제주에 있다고 보므로 한국 시간과 같다고 가정한다.

## 8. 성공 지표

- 허용 범위 안의 어떤 시작·끝 조합으로 만든 코스에서도 여행 시간이나 영업시간을 벗어난 정류장이 0개다 (자동 테스트로 확인).
- 14:00 이후에 시작하는 코스가 만들어진다 (지금은 불가능).
- 온보딩 단계 수가 늘지 않는다 (5단계 유지).
- 기존 테스트가 모두 통과한다.

## 9. 남은 질문

- (결정됨, 2026-11-13) 늦은 오후의 짧은 코스에서 후보가 모자랄 수 있는 문제: 지금은 장소가 제주시 원도심 19곳(식당 4곳, 카페 1곳)뿐이라 영업시간 필터 뒤에 `NO_CANDIDATES`가 날 수 있다. 장소 데이터를 제주도 전체로 늘리고 원도심 제한을 풀어서 해결한다 (`tasks/prd-start-area.md`). 이 문서에서는 따로 다루지 않고, 끝나는 시각 상한(22:00)도 그대로 둔다. 데이터가 늘기 전까지는 원도심의 늦은 오후 코스에서 `NO_CANDIDATES`가 날 수 있다.
- 16:00 이후에 앱을 열면 시작 시각의 처음 값이 `10:00`이 되는데, 코스는 오늘 요일 기준으로 만들어진다. "내일 코스"로 볼지, 안내 문구를 넣을지 정해야 한다.
- 2시간 코스의 정류장 수(2곳 고정)가 적절한지 실제 결과를 보고 조정한다.
